## Phase 1: 시안 분석 + 토큰 매칭 (코드 작성 전, 읽기 전용)

### 1-1. 시안 분석

첨부된 스크린샷을 분석해서 다음을 식별:

- 페이지/섹션 레이아웃 구조
- 재사용 가능한 컴포넌트 후보 (카드, 버튼, 탭 등)
- 시안에 존재하는 UI 요소 카테고리 (리스트/그리드, 폼, 모달, 이미지 다수, 인증 필요 등)
  → 이 목록이 Phase 2의 조건부 질문 트리거가 됨

### 1-2. 코드베이스 탐색 (읽기만)

다음을 순서대로 읽어:

1. `tailwind.config.ts` — 정의된 디자인 토큰 전체
2. `src/app/globals.css` — CSS 변수와 글로벌 스타일
3. `src/shared/ui/` — 기존 공용 UI 컴포넌트
4. 유사한 기존 페이지 1~2개 (있다면)

### 1-3. 토큰 후보 보고서

**중요: 스크린샷에서 정확한 픽셀 값을 추정하는 것은 신뢰할 수 없음.**
"~px일 것 같다"고 단정하지 말고, 토큰 후보를 가능성 순으로 제시할 것.

각 요소를 다음 두 카테고리 중 하나로 분류:

#### 카테고리 A: "사용자에게 물어볼 항목" (페이지 인상을 좌우)

- 페이지의 핵심 색상 (주요 액션 버튼, 강조색, 브랜드 컬러 영역)
- 페이지 헤더/타이틀의 타이포
- 토큰에 명백히 없는 특이값 (예: 부드러운 그림자, 특수 라디우스)
- 1회만 등장하는 시각적으로 두드러진 요소

#### 카테고리 B: "기본값으로 진행할 항목" (반복 사용되는 일반 요소)

- 표준 카드 패딩, 본문 텍스트 색, 일반 배경
- 기본 보더 라디우스, 일반 그림자
- 반복 요소 (5개 카드의 패딩이 똑같아 보이면 묶음 처리)
- → 가장 흔한 토큰값 자동 적용, 플랜에 "기본값 사용" 표시

다음 표 형태로 정리:

**카테고리 A (질문 필요):**

| 시안 요소             | 토큰 후보                                    | 확신도 |
| --------------------- | -------------------------------------------- | ------ |
| 주요 액션 버튼 색     | `bg-blue-500`, `bg-primary`, `bg-indigo-600` | 낮음   |
| 페이지 헤더 폰트 크기 | `text-2xl`, `text-3xl`                       | 중간   |

**카테고리 B (기본값 적용, 플랜에서 일괄 표시):**

| 시안 요소군      | 적용할 기본값   | 근거                     |
| ---------------- | --------------- | ------------------------ |
| 카드 패딩 (반복) | `p-6`           | 토큰 중 가장 흔한 패딩값 |
| 본문 텍스트      | `text-gray-700` | 기존 페이지 패턴         |
| 보더 라디우스    | `rounded-lg`    | 코드베이스 일관성        |

**확신도 기준:**

- **높음**: 코드베이스에 같은 패턴이 이미 존재 (참고 컴포넌트 명시)
- **중간**: 토큰 후보가 2~3개로 좁혀짐
- **낮음**: 시각적으로만 추정, 정확한 값 모름

**규칙:**

- 토큰에 없는 값이 필요하면 임의값(`p-[13px]`) 쓰지 말 것
- 카테고리 A만 Phase 2에서 질문
- 카테고리 B는 플랜 검토 시 사용자가 일괄 수정 가능 (질문하지 않음)

### 1-4. 컴포넌트 재사용 분석

- 기존 컴포넌트로 해결 가능한 부분
- 새로 만들어야 할 컴포넌트 (이름과 위치 제안)
- 기존 확장 vs 신규 결정 필요한 부분 → Phase 2 질문으로

## Phase 2: 인터뷰 (필요한 만큼만)

AskUserQuestion 도구로 결정 포인트만 물어봐.
**형식적으로 모든 차원을 묻지 말 것.**

### 항상 다루는 차원

1. **데이터 소스** — 서버 컴포넌트 직접 fetch vs 클라이언트 페치(SWR/TanStack)
   - **이미 API가 존재하면** 그 정보를 명시하고 응답 형태 확인만
2. **반응형** — 스크린샷은 한 뷰포트만 보이므로 항상 필요
3. **`'use client'` 경계** — 어디서부터 클라이언트 컴포넌트인지
4. **Phase 1의 카테고리 A 토큰** — 후보 중 어느 걸 쓸지

### 조건부로만 다루는 차원 (해당 요소가 시안에 있을 때만)

- **리스트/그리드 있을 때** — 무한 스크롤 vs 페이지네이션, 빈 상태 디자인
- **폼 있을 때** — 검증 시점, 에러 표시 위치, 제출 상태
- **모달/드롭다운 있을 때** — 닫기 동작, 키보드 처리, 포커스 트랩
- **이미지 많을 때** — next/image 외부 도메인 설정, alt 텍스트 소스
- **인증 필요할 때** — 로그인 안 된 경우 처리
- **동적 라우트일 때** — `generateStaticParams` 사용 여부
- **인터랙션 요소 있을 때** — 호버/포커스 상태가 시안에 있는지

### 질문 전 자가 점검 (체크리스트)

각 잠재 질문에 대해 다음을 자문:

1. 이 질문의 답이 작업 컨텍스트($ARGUMENTS)에 이미 있나? → 있으면 제외
2. 이 질문의 답이 코드베이스에서 명백한가? (기존 페이지 모두 SWR이면 SWR) → 명백하면 제외
3. 이 결정이 구현에 실질적 차이를 만드나? → 차이 없으면 제외
4. 이 차원이 시안에 있는 UI 요소와 관련 있나? → 무관하면 제외

위 중 어느 하나라도 "제외"면 질문하지 않음.

### 일괄 처리 규칙

- 같은 카테고리(예: 색상, 폰트)의 여러 질문은 한 번에 묶어서 제시
- 한 항목당 한 번씩 AskUserQuestion 호출하지 말 것
- 결정의 종속성이 있는 경우만 순차 진행

### 규칙

- 모호한 게 있으면 "이렇게 가정하고 진행"이 아니라 질문
- 단, 결정 포인트가 진짜 있을 때만. 형식적 질문 금지.

## Phase 3: 플랜 작성

인터뷰가 끝나면 다음 형식으로 단계 분할:

### 단계 형식 (3종 세트)

```
### 단계 N: [짧은 제목]
- 변경/생성 파일: src/...
- 변경 내용: 한두 줄 요약
- 검증 방법: `yarn tsc --noEmit` 통과 / 페이지 직접 확인 / 등
```

### 순서 규칙

1. **타입 정의** (`src/entities/[entity]/[entity].type.ts` 또는 `src/features/[feature]/[feature].type.ts`)
2. **UI 구현**
   - **케이스 A** (API 이미 존재 + 응답 형태 명확): 처음부터 실제 fetch로 구현
   - **케이스 B** (API 미존재 또는 응답 모름): 목 데이터로 먼저 UI 완성
3. **데이터 연결** — 케이스 B인 경우에만 별도 단계
4. **인터랙션** (클릭, 호버, 폼 등)
5. **반응형** (모바일/태블릿 브레이크포인트)
6. **접근성** (aria, 키보드, alt 텍스트)
7. **엣지 케이스** (로딩, 에러, 빈 상태)

### 크기 규칙

- 한 단계 = 1~3개 파일 (리뷰 가능한 크기)
- 7개 이상 파일을 건드릴 단계는 자동 분할
- 새 공용 UI 컴포넌트 생성은 별도 단계

### 플랜 끝에 포함할 것

- 변경되는 파일 전체 목록
- 사용할 디자인 토큰 목록 — **카테고리 B(기본값) 항목 표로 명시**
  → 사용자가 플랜 검토 시 일괄 수정 가능
- 새로 만드는 컴포넌트의 책임 한 줄 요약

## Phase 4: 실행 (마일스톤 승인 모드)

플랜을 사용자가 승인한 후 실행하되, **체크포인트에서 멈추고 확인 요청**.

### 체크포인트 구조

**체크포인트 1 — 단계 1~2 완료 후 (시각 확인)**

- 멈추고 보고:
  - 완료한 작업 요약
  - 직접 확인할 페이지 경로 (예: `http://localhost:3000/users/[id]`)
  - 적용한 카테고리 B 토큰 표 (기본값으로 진행한 것들)
- 사용자 응답 대기:
  - "OK" → 다음 체크포인트로
  - 수정 요청 → 같은 단계 내 수정 후 재확인

**체크포인트 2 — 단계 3~4 완료 후 (동작 확인)**

- 케이스 A면 단계 4(인터랙션) 완료 시점
- 케이스 B면 단계 3(데이터 연결) + 4(인터랙션) 완료 시점
- 멈추고 보고:
  - 데이터 연결 결과 (실제 응답 받아지는지)
  - 주요 인터랙션 동작 설명
- 사용자 응답 대기

**최종 — 단계 5~7 연속 진행 후**

- 반응형, 접근성, 엣지 케이스를 연속 처리
- 완료 후 최종 보고

### 실행 규칙

- 각 단계 끝나면 `yarn tsc --noEmit` 실행해서 통과 확인
- 단계 완료할 때마다 무엇을 했는지 1~2줄로 보고
- 실행 중 새 모호함 발견 시 즉시 멈추고 AskUserQuestion
- 임의값(`p-[13px]`, `text-[#xxx]`) 절대 사용 금지 — 토큰에 없으면 멈추고 질문
- 체크포인트가 아닌 곳에서는 자동 진행 (단계마다 멈추지 말 것)

### 완료 후 최종 보고

- 변경된 파일 전체 목록
- 직접 확인이 필요한 페이지 경로
- 알려진 미구현/유보 항목 (다음 PR로 넘긴 것들)
- 시안과 의도적으로 다르게 구현한 부분 (있다면 이유 포함)
